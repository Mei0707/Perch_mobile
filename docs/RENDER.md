# Render demo deployment

`render.yaml` is a reviewable deployment specification, not evidence of a deployed service. On October 26, 2026, deployment was kept local at the user’s request; no Render resources were provisioned. It creates one Docker web service in Oregon with plan `0.5c-512mb` and a 1 GB persistent disk mounted at `/app/data`. Automatic deployment on commits is disabled. The service exposes `/health` for liveness and protects `/v1/status` and all data/AI routes with a private viewer token.

At the pricing checked on October 26, 2026, this configuration is approximately **$7.25/month** ($7 compute plus $0.25 disk), before provider API usage, bandwidth overages, and taxes. Confirm the account's current billing terms before creating it. Persistent storage requires a paid Render service; this blueprint intentionally does not promise a durable quota on a free ephemeral filesystem. Sources: [Render pricing](https://render.com/pricing), [compute plan IDs](https://render.com/docs/compute-plans), [persistent disks](https://render.com/docs/disks).

## Prepared artifact

- Official Node container, non-root `node` user, no third-party dependencies.
- Image copies only the server's required modules. `.env`, credentials, reports, and tests are excluded.
- Production refuses short/whitespace tokens and missing provider keys at startup.
- Default limit: 50 submitted answers per UTC day, persisted before a request can spend API usage. Failed and canceled submissions still count. At most two LLM requests are possible within the current per-answer planning bounds; the submission count is not a dollar budget.
- Requests share a token-based minute limit across IPs; the backend does not trust forwarded client IPs. The quote provider also has a local request budget.
- Single instance with durable quota JSON. Do not scale replicas without replacing quota state with transactional shared storage. Provider/project billing limits remain necessary.

The image and isolated local container were verified with **dummy** provider keys: liveness, required authentication, authenticated configuration status, non-root/read-only isolation, and writable persistent storage. Those checks make zero provider requests.

## Deploy after account access is connected

1. Connect the repository to Render and use the root `render.yaml` blueprint. The current workspace changes must be committed/pushed to the intended branch before a Git-backed deployment can build them.
2. Review the service, disk, region, billing, and intended audience. The service is reachable over HTTPS, but every data/AI route requires its private token. Keep it an invite-only demonstration.
3. Set `OPENAI_API_KEY` and `FINNHUB_API_KEY` in Render's runtime secrets. `PERCH_API_TOKEN` is generated by Render; retrieve it privately from your dashboard and enter it into the app's Settings. Never place it in Swift source or share it publicly.
4. Confirm that the mounted directory is writable by the `node` user. Permission failures must be corrected before serving AI requests; quota write failures return an error and do not allow spending. Render disk mount behavior must still be verified on the deployed service.
5. Deploy and verify `/health` over HTTPS, unauthenticated `/v1/status` returns 401, and authenticated `/v1/status` reports configured keys. This status checks configuration, not provider authentication.
6. Set the deployment's HTTPS URL and token in Perch Settings. Use **Test saved connection**, add synthetic demo holdings, and run a real quote + chat scenario. Validate streaming through Render's actual proxy and record the resulting URL and benchmark report.
7. Confirm quota state survives restart, revoke/rotate the viewer token when demos end, and control analytics disk growth. The current demo has no automatic log retention/rotation; remove expired aggregate logs according to your policy. Do not delete the budget file to rotate logs.

This is a shared-token demonstration backend. It is not a public multi-user service and does not implement user accounts, brokerage access, cross-instance rate limiting, or a hard monetary spending cap.

## Reproduce local container verification

```sh
docker build -t perch-api:verification backend
node backend/verify-container.mjs
```

The verifier creates and deletes only its own container and uniquely named volume. A separate `backend/compose.yaml` is available for self-hosted testing with a real ignored `.env`. It binds to host loopback; put it behind a TLS reverse proxy if exposing it outside the machine.
